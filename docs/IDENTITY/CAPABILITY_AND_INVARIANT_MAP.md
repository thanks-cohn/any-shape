## Invariant trace

| Canonical invariant | Failure condition | Independent verification path |
|---|---|---|
| identity | A representation changes logical field/object/action meaning | Stable metadata/state comparison; human visual review separately |
| context | Local constraints ignored or used to remove meaning | Simultaneous unequal-container and resource/fallback stimuli |
| no-loss | Essential information/action becomes inaccessible | Geometry, complete payload validation, explicit unsupported probes |
| accessibility | Names, reading order, input access or feedback sacrificed | Native keyboard/form/label probes, axe and manual assistive review |
| no-js | Optional web diagnostics/enhancement becomes essential | Browser JS-disabled and physical optional artifact removal |
| privacy | Default diagnostics capture text/values/URLs or transmit | Unique synthetic canaries, log/request observation and schema checks |
| measured-truth | Hypothesis or absent evidence reported as fact/pass | Canonical closed-world evaluations, scoped report inspection |
| language-neutral | Language/vendor identity replaces behavioral obligations | Different-language reconstruction plus explicit untested target limits |
| shared-rules | Human/agent validation, authority or state diverge | Same valid/invalid payloads through both faces; revision comparison |
| safe-agent | Discovery, denied actor or missing consent changes state | Authorization/consent negatives and unchanged snapshots |
| unsupported | Unavailable feature becomes silent success/absence | Unsupported operation returns typed error and intact state |
| resource-resilience | Capacity loss silently drops meaning/function | Actual module/renderer loss; declared workload/resource probes for future targets |
| recoverability | A new agent cannot derive/evaluate a realization | Frozen neutral inputs, procedural blind trial, independent results |
| web-compatibility | Universal expansion breaks existing adopters | Existing 87 browser tests, unit/type/package/recovery; separate API migration checks |

## Evidence rules and gaps

`evidence.original-implementation` is historical. Fresh web and independent proof outputs have separate immutable hashes and scope. Verification definitions without executed evidence are plans, not claims. Future capability records may have no related implementation; canonical audit's `capability-no-implementation` is an honest finding, not something to remove by inventing a dummy renderer.

The Python candidate is not a production realization for all 17 capabilities. It exercises selected preferences/browser/text obligations. Candidate claims and migration evaluation MUST remain unknown/fail where scope is incomplete or drop-in obligations are unmet. New evidence may change a scoped result; it does not ratify technical provenance or prove unexecuted examples.
